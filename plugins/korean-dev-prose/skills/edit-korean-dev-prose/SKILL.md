# 주석과 개발 문서 교정

사용자가 지정한 글과 그 앞뒤를 읽고, 읽는 사람이 어느 대목에서 뜻을 다시 짚어야 하는지 찾는다.
파일을 고쳐 달라면 해당 부분을 직접 고치고, 문장만 건넸다면 그대로 붙여 쓸 수 있는 교정문을 준다.
이미 뜻이 분명한 문장은 원문을 살린다.
저장소에 주석이나 문서 작성 규칙이 있으면 그 용어와 예외를 먼저 확인한다.

## 주석을 지우기 전에

- 이 줄을 지우면 다음 사람이 무엇을 다시 알아내야 하는지 본다.
  `load(id)` 위의 `// ID로 조회한다`는 지운다.
  값을 고른 이유, 외부 서비스의 제약, 구버전과의 약속, 영어 필드명에 대응하는 업무 용어는 해당 코드 옆에 남긴다.
- 긴 함수에서 구간을 나누는 번호와 하위 번호는 살린다.
  여러 함수에 걸친 흐름은 진입점에서 각 단계가 정하는 것과 놓치기 쉬운 분기 순서를 짚는다.
- 같은 설명이 여러 곳에 있으면 그 동작을 정하는 코드에 한 번 쓰고 다른 곳에서는 가리킨다.
  다만 테스트 입력을 고른 이유나 UTC 일정을 현지 시각으로 읽는 법은 각 값을 보는 자리에서 필요하다.
  만료 시간을 넘긴 요청을 검사하는 테스트라면 그 경계를 넘기려고 고른 입력값 옆에 이유를 남긴다.
- ‘이번 PR에서’, ‘기존 방식’은 걷어내고 지금도 지켜야 하는 조건을 남긴다.
  실측값의 측정일이나 현재 제약을 설명하는 결정 링크는 그 근거와 함께 보존한다.
  아직 연결하지 않은 재시도나 확인하지 못한 외부 동작을 현재의 보장으로 쓰지 않는다.

## 문장을 다듬을 때

- 이유가 있어야 규칙을 이해할 수 있으면 업무에서 벌어지는 일을 먼저 쓴다.
  예를 들어 ‘승인 취소 시 검토 가능 상태 복원’은 ‘담당자가 승인을 취소하면 다른 담당자가 문서를 다시 검토할 수 있다’로 푼다.
- ‘그쪽’, ‘처리한다’, ‘다시 잡는다’에서 뜻이 갈리면 누가 무엇을 어디에 저장하거나 무엇을 다시 계산하는지 쓴다.
  ‘일정을 다시 잡는다’에서 달라지는 것이 알림 시각이라면 ‘새 마감일을 기준으로 알림 시각을 다시 계산한다’로 고친다.
  뜻이 하나로 읽히는 동사까지 일괄 치환하지 않는다.
- 같은 대상은 같은 이름으로, 같은 동작은 같은 동사로 쓴다.
  용어가 애매하면 주변 코드와 문서에서 팀의 용례를 찾는다.
  낯선 한자어나 새 번역어를 만들기보다 익숙한 한국어나 원래 기술 용어를 쓰고, 다른 시스템의 이름은 처음 나올 때 역할을 짚는다.
- ‘충분히 작으면’에는 비교 대상과 경계를 쓴다.
  바뀔 수 있는 설정은 이름으로 가리키고, 경계에서 결과가 갈리거나 값의 형식이 낯설면 실제 입력과 결과 한 쌍을 보여 준다.
- 한국어 README는 합니다체로, 주석과 에이전트 지침은 한다체로 쓴다.
  본문은 한 줄에 한 문장을 쓰고, 긴 설명은 뜻이 끊기는 곳에서 나눈다.
  굵은 글씨는 놓치면 안 되는 보장이나 경고에만 쓴다.

## 문서에서 설명할 범위

README에는 사람이 알아야 할 목적과 직접 따라 할 절차를 둔다.
특정 모듈의 절차는 그 모듈의 README로 연결한다.
AGENTS.md에는 작업을 시작할 파일·함수, 업무 용어, 지켜야 할 제약을 둔다.
구현에서 확인할 수 있는 필드 목록과 설정 기본값은 복사하는 대신 해당 정의로 연결한다.
문서에서 덜어 낼 문장에 유일한 업무상 이유가 있다면, 편집 범위 안에서는 그 결정이 쓰인 코드 옆으로 옮기고 범위 밖이면 원문을 보존하고 옮길 곳을 짚는다.

## 교정한 뒤

바꾼 설명의 조건·단위·예외를 구현이나 제공된 자료와 대조한다.
근거가 없으면 원문의 의미를 보존하고 무엇을 확인해야 하는지 따로 짚는다.
주석 교정에서는 diff를 보고 실행 코드, 로그·예외 문자열, 테스트 이름까지 바뀌지 않았는지 확인한다.
외부에 그대로 노출되는 API 설명이나 CLI 도움말을 일반 주석과 함께 일괄 교정하지 않는다.
